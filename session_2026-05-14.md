## 1. Transverse Isotropic Constitutive Model for FDM-Printed PLA

### 1.1 Physics Motivation

FDM (Fused Deposition Modelling) prints successive layers of melted filament. The bond between layers forms at a temperature lower than the melt temperature of the filament itself, producing a region of reduced molecular diffusion and crystallinity. This makes FDM parts **mechanically anisotropic**: properties along the in-plane raster directions (parallel to deposited filaments) differ measurably from properties across the layer interfaces (the build axis).

For symmetric in-plane raster patterns (0°/90° alternating or concentric), the in-plane directions are statistically equivalent and the material is **transversely isotropic**: one weak axis (build/print direction) and one isotropic strong plane (the layer plane).

**Literature basis** (values pinned to measurements):
- Perez, Celik & Karkkainen (2021), *3D Print. Addit. Manuf.* 8(1), PMC9828590
  - Measured $E_z = 2.4\ \text{GPa}$ vs filament $E = 3.57\ \text{GPa}$ → $E_z/E_p \approx 0.67$
  - Measured $\sigma_z = 22.8\ \text{MPa}$ vs filament $\sigma = 43.6\ \text{MPa}$ → $\sigma_z/\sigma_p \approx 0.52$
  - Interlayer failure attributed to "imperfect interlayer bonding as the primary mechanism"
- Springer (2025), DOI 10.1007/s00170-025-16785-0: Tsai-Wu is the gold standard failure criterion; **max-stress per mode is an accepted simpler alternative** for qualitative visualization

### 1.2 Five Independent Constants

A transversely isotropic solid with the build axis as the symmetry axis has **five independent elastic constants**:

| Symbol | Meaning |
|--------|---------|
| $E_p$ | Young's modulus in the strong (in-plane) directions |
| $E_z$ | Young's modulus along the build (weak) axis |
| $\nu_p$ | In-plane Poisson's ratio (strong–strong coupling) |
| $\nu_{pz}$ | Out-of-plane Poisson's ratio (strong–weak coupling) |
| $G_{pz}$ | Transverse shear modulus (strong–weak planes) |

The in-plane shear modulus is **not independent** — it is derived from the isotropy condition in the strong plane:
$$G_p = \frac{E_p}{2(1+\nu_p)}$$

The symmetry constraint $\nu_{pz}/E_p = \nu_{zp}/E_z$ ensures the $3 \times 3$ normal-stress compliance block is symmetric.

### 1.3 Compliance Matrix and Inversion

The $6 \times 6$ constitutive matrix $D$ maps engineering Voigt strain $\varepsilon = [\varepsilon_{xx},\varepsilon_{yy},\varepsilon_{zz},\gamma_{xy},\gamma_{yz},\gamma_{xz}]^T$ to Cauchy stress $\sigma = D\varepsilon$.

It is constructed by inverting the $3\times3$ normal-stress compliance block $S$ and placing the shear moduli on the diagonal. The form of $S$ depends on which global axis is the build (weak) axis.

#### Build axis = Z (Z weak, XY strong plane)

$$S = \begin{bmatrix}
1/E_p & -\nu_p/E_p & -\nu_{pz}/E_p \\
-\nu_p/E_p & 1/E_p & -\nu_{pz}/E_p \\
-\nu_{pz}/E_p & -\nu_{pz}/E_p & 1/E_z
\end{bmatrix}$$

Shear diagonal: $D_{33}=G_p$ (XY in-plane), $D_{44}=D_{55}=G_{pz}$ (YZ, XZ transverse).

#### Build axis = Y (Y weak, XZ strong plane) — default

$$S = \begin{bmatrix}
1/E_p & -\nu_{pz}/E_p & -\nu_p/E_p \\
-\nu_{pz}/E_p & 1/E_z & -\nu_{pz}/E_p \\
-\nu_p/E_p & -\nu_{pz}/E_p & 1/E_p
\end{bmatrix}$$

Shear diagonal: $D_{33}=D_{44}=G_{pz}$ (XY, YZ transverse), $D_{55}=G_p$ (XZ in-plane).

#### Build axis = X (X weak, YZ strong plane)

$$S = \begin{bmatrix}
1/E_z & -\nu_{pz}/E_p & -\nu_{pz}/E_p \\
-\nu_{pz}/E_p & 1/E_p & -\nu_p/E_p \\
-\nu_{pz}/E_p & -\nu_p/E_p & 1/E_p
\end{bmatrix}$$

Shear diagonal: $D_{33}=D_{55}=G_{pz}$ (XY, XZ transverse), $D_{44}=G_p$ (YZ in-plane).

In all cases: $D[0:3,\ 0:3] = S^{-1}$ (computed via `Eigen::Matrix3d::inverse()`), with the rest zero.

**SPD condition**: For valid FDM-PLA parameters ($E_z < E_p$, $\nu_{pz} < 0.5$, $G_{pz} > 0$), $S$ is positive definite and $D$ is positive definite. The assembled global stiffness $K = \sum_e A_e^T K_e A_e$ inherits positive definiteness after penalty BC enforcement.

## 2. Mode-Aware Fracture Criterion for FDM Parts

### 2.1 Motivation

Isotropic von Mises stress treats all failure modes identically. For FDM PLA, failure occurs by three physically distinct mechanisms with different thresholds:

| Mode | Physical mechanism | Stress quantity | Threshold |
|------|--------------------|----------------|-----------|
| Interlayer tensile | Layer separation under tension normal to the interface | $\max(\sigma_\perp,\ 0)$ | $\sigma_\text{interlayer}$ |
| Interlayer shear | Sliding between layers | $\sqrt{\tau_{\perp 1}^2 + \tau_{\perp 2}^2}$ | $\tau_\text{interlayer}$ |
| Intralayer | In-plane filament fracture | 2D von Mises in strong plane | $\sigma_\text{intralayer}$ |

The $\max(\cdot, 0)$ guard on the interlayer tensile check is physically motivated: compressive stress normal to the layer interface closes the gap and does not cause delamination.

### 2.2 In-Plane Von Mises for Transverse Isotropy

For a body that is isotropic in the $ij$-plane, the plane-stress von Mises stress in that plane is:
$$\sigma_\text{vM,in-plane} = \sqrt{\sigma_{ii}^2 - \sigma_{ii}\sigma_{jj} + \sigma_{jj}^2 + 3\tau_{ij}^2}$$

This is the exact limit of the 3D von Mises formula restricted to the two in-plane normal stresses and the in-plane shear. It is mathematically rigorous under the transverse isotropy assumption.

### 2.3 Build-Axis-Dependent Index Mapping

Voigt ordering: $[\sigma_{xx},\sigma_{yy},\sigma_{zz},\tau_{xy},\tau_{yz},\tau_{xz}]$, indices $s(0)\ldots s(5)$.

| `buildAxis` | Weak axis | Strong plane | $\sigma_\perp$ | $\tau_\perp$ pair | In-plane $\sigma_\text{vM}$ |
|-------------|-----------|--------------|----------------|--------------------|-----------------------------|
| 2 | Z | XY | $s(2)$ | $s(4), s(5)$ | $\sqrt{s(0)^2-s(0)s(1)+s(1)^2+3s(3)^2}$ |
| 1 | Y | XZ | $s(1)$ | $s(3), s(4)$ | $\sqrt{s(0)^2-s(0)s(2)+s(2)^2+3s(5)^2}$ |
| 0 | X | YZ | $s(0)$ | $s(3), s(5)$ | $\sqrt{s(1)^2-s(1)s(2)+s(2)^2+3s(4)^2}$ |

These index assignments were derived by applying the symmetry definitions of transverse isotropy to the general 3D von Mises expression and selecting the appropriate normal and shear components for each principal material coordinate system.

## 4. Symmetric Tension Load Types (TensionX / TensionY / TensionZ)

### 4.1 Physics: Symmetric Tension Test

A symmetric tension test applies equal and opposite forces on two opposite faces, replicating a uniaxial tensile test. Unlike a cantilever test (which induces a bending stress gradient), symmetric tension induces a nearly uniform axial stress field — ideal for characterizing interlayer failure because the stress normal to the layer interface is maximally amplified for the FDM build axis.

Applied forces:
$$F_i^+ = +\frac{F_\text{total}}{N_+}, \quad i \in \text{face}^+\qquad F_j^- = -\frac{F_\text{total}}{N_-}, \quad j \in \text{face}^-$$

where $N_\pm$ is the number of nodes on each face. The load vectors on both faces are equal in magnitude and opposite in sign, so the net applied force is zero — the system is self-equilibrating and rigid-body motion must be prevented by minimal constraints only.

Face detection: nodes with axis coordinate within 2% of the bounding-box extreme are collected as face nodes.

### 4.2 3-2-1 Minimal Rigid-Body Constraint

A free body in 3D has 6 rigid-body modes (RBMs): 3 translations $t_x, t_y, t_z$ and 3 rotations $r_x, r_y, r_z$. For a self-equilibrating load (net force = 0, net moment = 0), any solution to $Ku=F$ is defined only up to these 6 RBMs. The stiffness matrix $K$ would be singular without additional constraints.

The **3-2-1 scheme** applies exactly 6 scalar DOF constraints to prevent all 6 RBMs without over-constraining the strain field:

1. **Node A** (nearest mesh centroid) — fix all 3 DOF → prevents $t_x, t_y, t_z$
2. **Node B** (maximum offset from A along perpendicular axis $p_b = (a+1)\%3$) — fix DOF $p_c = (a+2)\%3$ → prevents the rotation about the tension axis
3. **Node C** (maximum offset from A along perpendicular axis $p_c$, excluding A and B) — fix DOF $p_b$ → prevents the remaining rotation

Here $a$ is the tension axis index. For $a=0$ (TensionX): $p_b=1$ (Y), $p_c=2$ (Z). Nodes B and C are chosen by maximum offset in the respective perpendicular axis to maximize the moment arm of the constraint, improving numerical stability.

The 6 constraints are applied via the penalty method with $\alpha = 10^7 \times \max(\text{diag}(K))$, consistent with the existing Dirichlet BC enforcement.

**Over-constraint analysis**: Fixing node A with all 3 DOF technically applies 3 constraints for 3 translations, but also constrains rotational modes through that point. The additional 2 single-DOF constraints at B and C complete the 6-constraint set. For a non-centrosymmetric mesh, the RBMs are prevented without artificially restraining the principal strain (axial elongation along the tension axis).

## 6. GPU and Multithreading Fix for `solveBrittleFracture`

### 6.1 Bug 1: Island-Node Singularity Breaks GPU Cholesky

**Root cause**: As the fracture loop kills elements, nodes whose *last* connected element is removed become "island nodes" — they have no stiffness contributions and their DOF rows in $K$ are identically zero:

$$K_{ii} = \sum_{e : i \in e} B_e^T D B_e \cdot V_e = 0 \quad \text{if all } e \text{ containing node } i \text{ are dead}$$

A zero-diagonal entry makes $K$ singular (not positive definite). The GPU PCG solver (cuSPARSE + cuBLAS Jacobi-preconditioned CG) requires non-singular $K$ — a zero diagonal entry causes division by zero in the Jacobi preconditioner (`z[i] = r[i] / diag[i]`), which in practice sets `useGPU = false` on the `FEASolver` object — permanently, for all remaining iterations.

**Fix: [src/FEASolver.cpp:592](src/FEASolver.cpp#L592)** — After `K.setFromTriplets()`, when running inside the fracture loop (`m_fractureAlive` is non-empty), scan the diagonal and add $K_{ii} = 1$ for any zero entry:

```cpp
// src/FEASolver.cpp:592
if (!m_fractureAlive.empty()) {
    const VectorXd diag = K.diagonal();
    for (int i = 0; i < nDOFs; ++i)
        if (diag[i] == 0.0) K.coeffRef(i, i) = 1.0;
}
```

**Physical correctness**: An island node has no stiffness connection to the rest of the structure. Its equilibrium displacement is $u_i = 0$ (it stays in place). Setting $K_{ii} = 1$ and $F_i = 0$ (from the BC zeroing) gives exactly this result. The displacement field everywhere else is unaffected because island nodes are decoupled from the rest of the system.

**Conditioning effect**: The penalty BC sets fixed-node diagonals to $\sim 10^7 \times K_\text{max}$. Island-node diagonals are set to $1$. The Jacobi preconditioner in the CG path normalizes each by its diagonal, so the island DOFs scale to approximately $1 \cdot F_i / 1 = 0$, consistent with zero displacement. This does not degrade the condition number of the system restricted to the alive DOFs.

### 6.2 Bug 2: Permanent `useGPU = false` Across Fracture Iterations

**Root cause**: In `solveLinearStatic`, when the GPU solve fails, the fallback handler sets `this->useGPU = false` to skip GPU on subsequent calls in the *same solver run*. But `solveBrittleFracture` calls `solveLinearStatic` repeatedly in a loop — so a single failure in iteration $k$ permanently disables GPU for iterations $k+1 \ldots N$.

**Fix: [src/FEASolver.cpp:2325](src/FEASolver.cpp#L2325)** — Save the user's intent before the loop and restore it at the top of each iteration at **[src/FEASolver.cpp:2328](src/FEASolver.cpp#L2328)**:

```cpp
// src/FEASolver.cpp:2325
const bool savedUseGPU = useGPU;
for (int iter = 0; iter < maxIters; ++iter) {
    // src/FEASolver.cpp:2328
    useGPU = savedUseGPU; // re-enable GPU; island-node fix ensures K is SPD
    m_fractureAlive = model.elementAlive;
    bool ok = solveLinearStatic(model, visualScale, &U);
    // ...
}
```

With the island-node fix in place (Bug 1 above), the GPU PCG succeeds on every iteration because $K$ is always SPD. The `savedUseGPU` restore provides defense-in-depth: if GPU fails for any other reason (VRAM pressure, driver issue), the user's flag is still honored on the next iteration.

### 6.3 Multithreading: Already Correct

The per-element stress recovery in `solveBrittleFracture` was already parallelized with `#pragma omp parallel for schedule(static) if(useMultithreading)`. Thread safety holds because:
- Each iteration writes to `sigmaVM[el]` and `failModeBuf[el]` at a unique index
- `model.elementAlive` and `U` are read-only during the parallel region
- Each thread constructs its own stack-local `TetrahedralElement`/`Tet10Element` object
- `TransverseIsotropicMaterial::ComputeConstitutive` is `const`, writes only to its stack-local `D` argument

The MT element assembly in `solveLinearStatic` (pre-sized disjoint triplet slots) also handles the fracture alive-mask correctly: dead elements are skipped via `if (!m_fractureAlive[el]) continue` inside the parallel loop, and since the triplet slot is pre-allocated for all elements, the skip just leaves those slots as zero-valued triplets that contribute nothing to `setFromTriplets`.

## 9. Key Design Decisions

**Why transverse isotropy, not full orthotropy?**
For symmetric raster patterns (0°/90° alternating or concentric), the in-plane directions are statistically equivalent. Orthotropy (distinguishing along-bead vs cross-bead) requires an additional modulus and a raster-orientation parameter per element — significantly more complexity for a feature that is not observable in this solver's geometry model. Transverse isotropy is the conventional simplifying assumption used by the majority of FDM-FEA literature.

**Why max-stress per mode, not Tsai-Wu?**
Tsai-Wu is the quadratic interaction criterion gold standard (Springer 2025). It requires an additional interaction coefficient $F_{12}$ and couples the failure modes. For qualitative visualization of layer-vs-non-layer failure, max-stress per mode is a widely-cited simplification that clearly separates failure modes and is easier to calibrate. Tsai-Wu is the natural next step for load-certification accuracy.

**Why `buildAxis` default = 1 (Y)?**
The user's FDM models are imported with Y as the vertical (print-top) direction in the coordinate system. Setting Y as the default weak axis means the FDM anisotropy is physically correct for the user's models without requiring a manual toggle.

**Why island-node regularization instead of eliminating island DOFs?**
Eliminating island DOFs would require rebuilding the global DOF numbering on every fracture iteration — expensive and complex. Setting $K_{ii}=1$ for island DOFs is $O(n_\text{DOF})$, preserves the matrix dimension across iterations, and produces physically correct $u_i = 0$ for unconstrained island nodes.

## 10. 3MF File Import Implementation

### 10.1 File Structure

**Files:**
- **[include/ThreeMFLoader.h](include/ThreeMFLoader.h)** — public interface and helper structs (89 lines)
- **[src/ThreeMFLoader.cpp](src/ThreeMFLoader.cpp)** — full implementation (607 lines)

The `.3mf` format is a ZIP archive containing an XML document (`3D/3dmodel.model`) that describes mesh geometry. Two variants are relevant:

| Variant | Structure | Behavior |
|---------|-----------|----------|
| **Standard 3MF** | Single `3D/3dmodel.model` with all geometry inline | All `<object>` elements are parsed in one pass |
| **Bambu Studio project .3mf** | `3D/3dmodel.model` contains only component references (`p:path` attribute on `<component>`) pointing to separate ZIP entries (e.g. `3D/Objects/part_0.model`) | Requires a two-pass load: extract each component's ZIP entry and parse it separately |
| **Bambu `.gcode.3mf`** (sliced export) | No mesh geometry at all — only toolpath G-code | Detected and diagnosed by the loader |

### 10.2 Public Interface (`include/ThreeMFLoader.h`)


### 10.3 XML Scanner Helpers (`src/ThreeMFLoader.cpp:25–270`)

| Function | Lines | Purpose |

### 10.4 XML State Machine: `parseModelXml` (`src/ThreeMFLoader.cpp:275–461`)

The parser uses a `Scope` enum to track which XML element it is currently inside:

```
Scope {None, Object, Vertices, Triangles, Build, Components}
```

The parser advances character-by-character through the XML string looking for `<` tag boundaries. On each opening tag it checks the tag name and transitions scope; on each closing tag it pops scope. The 3MF standard uses XML namespaces but the scanner strips them (looks at the local name only).

**Key state transitions and actions:**

| Transition | Action |
|------------|--------|
| `<object id="N" ...>` encountered | If `objectIdFilter < 0` or `id == objectIdFilter`: begin accumulating vertices/triangles into local buffers; record `objectId = N`. Otherwise skip. |
| `<vertices>` inside Object scope | Enter Vertices scope |
| `<vertex x="..." y="..." z="...">` | Append `{x,y,z}` to the current object's vertex list |
| `<triangles>` inside Object scope | Enter Triangles scope |
| `<triangle v1="..." v2="..." v3="...">` | Append `{v1,v2,v3}` offsets (relative to vertex base of this object) to FEAModel |
| `</object>` | Merge the object's vertices into `out.positions`; patch triangle indices to be global |
| `<build>` | Enter Build scope |
| `<item objectid="N" transform="...">` inside Build | Record a `BuildItem{objectId, transform}` |
| `<components>` inside Object scope | Enter Components scope |
| `<component objectid="N" p:path="..." transform="...">` | Record a `ComponentRef{parentObjectId, childObjectId, path, transform}` |

**Vertex base tracking**: Each `<object>` appends to `out.positions`. Triangle indices within an object are relative to its own vertex list. On closing `</object>`, the parser records the vertex base offset (position count before this object) and adds it to each triangle index so all indices are global.

### 10.5 Top-Level Loader: `ThreeMFLoader::load` (`src/ThreeMFLoader.cpp:466–606`)

```
1. Open ZIP with mz_zip_archive_init + mz_zip_reader_init_file.
2. Locate and extract "3D/3dmodel.model" entry.
3. Call parseModelXml(xml, out, -1, buildItems, componentRefs).
4. if out.positions.empty() && !componentRefs.empty():
       → Bambu multi-file branch (see below)
   elif out.positions.empty():
       → ".gcode.3mf diagnosis" branch (see below)
5. Close ZIP.
```

**Bambu multi-file branch** (when primary model has only component references, no inline geometry):

```
for each ComponentRef cr in componentRefs:
    if cr.path is empty: skip (intra-file reference, already merged)
    locate ZIP entry at cr.path (e.g. "3D/Objects/part_0.model")
    extract to string
    vertexBase = out.positions.size()
    call parseModelXml(xml, out, cr.childObjectId, dummy, dummy)
    apply cr.transform to vertices [vertexBase, end) via applyMat34
```

The `applyMat34` function interprets the 3×4 column-major Bambu transform:
```
[m0 m3 m6 m9 ]   [ R | t ]   with R = 3x3 rotation/scale, t = translation
[m1 m4 m7 m10] =  [       ]
[m2 m5 m8 m11]
```
Applied as: `v_world = R * v_local + t`.

**`.gcode.3mf` diagnosis branch**: If neither inline geometry nor component references are found, the loader checks for `.gcode` file entries in the ZIP (Bambu sliced exports always contain toolpath `.gcode` files). If found, it logs:
```
[3MF] Detected Bambu .gcode.3mf — this is a sliced export. No geometry available.
```

### 10.6 Dependency: miniz

The ZIP decompression uses **miniz** (single-header library, `ext/miniz/miniz.h`). Relevant API:
- `mz_zip_reader_init_file` — open ZIP from file path
- `mz_zip_reader_locate_file` — find a named entry
- `mz_zip_reader_extract_to_heap` — decompress entry to malloc'd buffer
- `mz_zip_reader_end` — close and free

No other external XML or ZIP library is used.

## 11. GPU Solver Implementation (Jacobi-PCG on cuSPARSE + cuBLAS)

### 11.1 Files

- **[include/CudaSolver.h](include/CudaSolver.h)** — public interface (30 lines)
- **[src/CudaSolver.cu](src/CudaSolver.cu)** — implementation (416 lines)

### 11.2 Why Iterative PCG Instead of Direct Sparse Cholesky

The original design intended to use `cusolverSpDcsrlsvchol` (GPU sparse Cholesky). This was replaced with Preconditioned Conjugate Gradient (PCG) because of the **fill-in** problem:

During Cholesky factorization $K = LL^T$, the sparse lower triangular factor $L$ gains non-zero entries ("fill-in") wherever the elimination ordering allows a fill path. For a 3D FEA stiffness matrix assembled from tetrahedral elements, the bandwidth is large and fill-in creates a nearly-dense factor. Empirically: a 3D FEA mesh with 36 million non-zeros in $K$ can produce a Cholesky factor $L$ with 180–720 million non-zeros (5–20× expansion), requiring 1.5–6 GB of VRAM — exceeding the 4 GB VRAM limit of many desktop GPUs.

**PCG has no fill-in**: the algorithm only performs SpMV (sparse matrix-vector multiply) $Ap$ on the original $K$. Memory usage is $O(\text{nnz} + n)$ — just the original matrix plus a handful of length-$n$ vectors:

```
VRAM ≈ nnz*12 bytes (vals, colIdx) + (n+1)*4 bytes (rowPtr) + 7*n*8 bytes (vectors)
     = 36M*12 + 458K*4 + 7*458K*8 ≈ 400 MB + 26 MB = 426 MB  ← fits in 4 GB
```

### 11.3 Public Interface (`include/CudaSolver.h:14–30`)

```cpp
// include/CudaSolver.h
namespace cuda_solver {
    bool isGpuAvailable();               // check CUDA device count
    std::string getGpuInfo();            // name, VRAM, SM count
    bool solveOnGpu(const Eigen::SparseMatrix<double>& K,
                    const Eigen::VectorXd& F,
                    Eigen::VectorXd& U); // Jacobi-PCG solve
}
```

Eigen's `SparseMatrix<double>` (default column-major = CSC format) is passed directly. For symmetric $K$, CSC == CSR (the matrix equals its own transpose in terms of which rows/columns are populated), so no format conversion is needed.

### 11.4 CUDA Kernels (`src/CudaSolver.cu:71–119`)

Five custom CUDA kernels are written to avoid host-device synchronization within the PCG loop:

| Kernel | Lines | Operation | Purpose |
|--------|-------|-----------|---------|
| `jacobiApply` | 71 | `z[i] = r[i] / diag[i]` | Apply Jacobi preconditioner element-wise |
| `computeAlphaDevice` | 80 | `alpha = rz/pAp; minus_alpha = -alpha` | Compute CG step length fully on GPU |
| `computeBetaDevice` | 86 | `beta = rz_new/rz; rz = rz_new` | Update CG direction coefficient on GPU |
| `vecAxpyDevicePtr` | 92 | `y[i] += *alpha * x[i]` | AXPY with device-pointer scalar |
| `vecXpBetaYDevicePtr` | 99 | `y[i] = x[i] + *beta * y[i]` | Direction update with device-pointer scalar |
| `extractDiagonal` | 106 | `diag[row] = K[row,row]` | Extract diagonal from CSR for Jacobi preconditioner |

The critical design choice is using **device-pointer mode** for cuBLAS scalars (`cublasSetPointerMode(CUBLAS_POINTER_MODE_DEVICE)`). This keeps all dot products and norms on the GPU, avoiding the round-trip `GPU → CPU → GPU` synchronization that would otherwise stall the PCG loop every iteration. The `computeAlphaDevice` and `computeBetaDevice` single-thread kernels consume the cuBLAS dot-product results (which are device pointers) and produce the next iteration's scalars without any host involvement.

### 11.5 Solver Algorithm (`src/CudaSolver.cu:152–414`)

The full `solveOnGpu` function implements Jacobi-preconditioned CG. Below is the algorithm structure with line references:

**Step 1 — Allocate GPU memory** ([lines 200–219](src/CudaSolver.cu#L200))

```
d_rowPtr   (n+1) ints     — CSR row pointer (= Eigen outerIndexPtr)
d_colIdx   nnz ints       — CSR column indices (= Eigen innerIndexPtr)
d_vals     nnz doubles    — matrix values (= Eigen valuePtr)
d_b        n doubles      — RHS vector F
d_x        n doubles      — solution vector (initialized to 0)
d_r        n doubles      — residual r = b - K*x
d_z        n doubles      — preconditioned residual z = M^-1 * r
d_p        n doubles      — search direction
d_Ap       n doubles      — matrix-vector product K*p
d_diag     n doubles      — Jacobi preconditioner (diagonal of K)
d_rz, d_rz_new, d_pAp, d_alpha, d_minus_alpha, d_beta   — scalar temporaries (device memory)
```

**Step 2 — Host to device transfer** ([lines 224–228](src/CudaSolver.cu#L224))

```cpp
cudaMemcpy(d_rowPtr, K.outerIndexPtr(), ...)
cudaMemcpy(d_colIdx, K.innerIndexPtr(), ...)
cudaMemcpy(d_vals,   K.valuePtr(),      ...)
cudaMemcpy(d_b,      F.data(),          ...)
cudaMemset(d_x, 0, ...)   // initial guess x0 = 0
```

**Step 3 — Extract Jacobi preconditioner** ([lines 248–252](src/CudaSolver.cu#L248))

```cpp
// src/CudaSolver.cu:250
extractDiagonal<<<(n+255)/256, 256>>>(d_rowPtr, d_colIdx, d_vals, d_diag, n);
```

Each thread handles one row, scanning its CSR entries for the diagonal element. Default value is 1.0 (avoids division by zero for island nodes, consistent with the island-node regularization in the CPU assembly).

**Step 4 — Create cuSPARSE handle and descriptors** ([lines 257–280](src/CudaSolver.cu#L257))

```cpp
cusparseCreate(&spHandle);       // SpMV handle
cublasCreate(&blHandle);         // dot-product / norm handle
cusparseCreateCsr(&matA, ...);   // CSR matrix descriptor
cusparseCreateDnVec(&vecP, ...); // dense vector p
cusparseCreateDnVec(&vecAp, ...);// dense vector Ap
// query + allocate SpMV work buffer
cusparseSpMV_bufferSize(..., &bufSize);
cudaMalloc(&spBuf, bufSize);
```

**Step 5 — PCG initialization** ([lines 285–308](src/CudaSolver.cu#L285))

```
r = b           (since x0 = 0, initial residual = b)
bNorm = ||b||   (cuBLAS nrm2; host pointer to compute target tolerance)
switch to DEVICE pointer mode for all subsequent cuBLAS calls
z = M^-1 * r    (jacobiApply kernel)
p = z
rz = r · z      (cuBLAS ddot, result in d_rz on device)
```

**Step 6 — PCG main loop** ([lines 314–366](src/CudaSolver.cu#L314)):

```
for iter = 0..MAX_ITER:
    Ap = K * p                    (cusparseSpMV, alpha=1 beta=0 HOST pointers required)
    pAp = p · Ap                  (cublasDdot, result in d_pAp on device)
    computeAlphaDevice<<<1,1>>>   (d_alpha = d_rz / d_pAp)
    x = x + alpha * p             (vecAxpyDevicePtr)
    r = r - alpha * Ap            (vecAxpyDevicePtr with minus_alpha)

    every 50 iterations (convergence check):
        switch to HOST pointer mode
        rNorm = ||r||  (cublasDnrm2, host scalar)
        if rNorm < target: break
        switch back to DEVICE pointer mode

    z = M^-1 * r                  (jacobiApply)
    rz_new = r · z                (cublasDdot, device)
    computeBetaDevice<<<1,1>>>    (d_beta = d_rz_new / d_rz; update d_rz)
    p = z + beta * p              (vecXpBetaYDevicePtr)
```

**Convergence criterion**: $\|r\|_2 < 10^{-9} \|b\|_2$. Checked every 50 iterations to amortize the host-device sync (switching pointer mode requires a `cudaDeviceSynchronize` implicitly via nrm2). Progress is printed every 500 iterations.

**Step 7 — Device to host and cleanup** ([lines 381–414](src/CudaSolver.cu#L381))

```cpp
U.resize(n);
cudaMemcpy(U.data(), d_x, n * sizeof(double), cudaMemcpyDeviceToHost);
// ... all cudaFree + cusparseDestroy + cublasDestroy calls
```

Cleanup is reached via `goto fail` on any CUDA/cuSPARSE/cuBLAS error, ensuring no GPU memory leaks regardless of which step fails.

### 11.6 Error Handling Pattern

Three `*_CHECK_GOTO` macros ([lines 36–64](src/CudaSolver.cu#L36)) handle errors from CUDA, cuSPARSE, and cuBLAS respectively. On any error, they print a diagnostic to `stderr` and jump to `fail:` label, which runs all cleanup and returns `false`. The caller in `solveLinearStatic` tests the return value and falls back to CPU if `false`:

```cpp
// In FEASolver.cpp — GPU path
if (useGPU) {
    success = cuda_solver::solveOnGpu(K, F, U);
    if (!success) {
        useGPU = false;  // this mutation is the one guarded by savedUseGPU in solveBrittleFracture
        // fall through to CPU path
    }
}
```

### 11.7 cuSPARSE SpMV Pointer Mode Asymmetry

A subtle implementation detail: cuSPARSE's `cusparseSpMV` requires its `alpha` and `beta` scalar arguments to be **host pointers** (even when cuBLAS is in device-pointer mode). This means the SpMV `Ap = 1.0*K*p + 0.0*Ap` must pass `&alpha` and `&beta` as stack-local doubles, while immediately afterwards `cublasDdot` is called with device pointers. The pointer mode switch is handled by keeping the two local double variables `alpha=1.0`, `beta=0.0` on the stack at [line 317](src/CudaSolver.cu#L317):

```cpp
// src/CudaSolver.cu:317
double alpha = 1.0, beta = 0.0;
cusparseSpMV(..., &alpha, matA, vecP, &beta, vecAp, ...);
```

This is the reason cuBLAS and cuSPARSE are deliberately kept in different pointer modes simultaneously within the loop.
