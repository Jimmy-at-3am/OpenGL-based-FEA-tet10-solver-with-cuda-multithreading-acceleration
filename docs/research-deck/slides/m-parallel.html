CPU multithreading and CUDA acceleration

CPU · OpenMP and worker threads [36]

Assembly uses every core with no locks, and the window never freezes.

Lock-free assembly parallel loop over elements; the triplet list is sized up front and element e writes only its own block, with private Ke buffers per thread; shared nodes are summed once at the end, so the answer equals the serial path

Cancel inside a parallel loop a parallel loop cannot break, so a shared atomic flag is checked every 1,024 elements

Parallel per-element work element setup, stress recovery and, in fracture runs, the per-element DB matrix computed once and reused every iteration

Multithreaded CG Eigen's CG on the full symmetric matrix, which lets the sparse product Kp run on all threads [35]

Thread budget two hardware threads stay free for the renderer; the worker runs below normal priority

Front end vs heavy work slicing and meshing run on a worker thread that never calls OpenGL (uploads wait for the render thread); solves run in a separate worker process, so Hard Stop can end them safely

GPU · CUDA PCG [37, 38]

Large meshes solve without leaving GPU memory: 2.9× faster at 367,000 elements.

Upload once K as row-major CSR (32-bit indices, doubles) and F; the matrix never comes back

Block preconditioner each node's own 3 × 3 block of K is inverted; weak blocks fall back to the diagonal; the same rule as CPU CG [27]

One iteration on the device one cuSPARSE CSR product Kp plus small vector kernels; cuBLAS dot products stay in device memory, so α and β are formed on the GPU with no host sync [39]

Every 50 iterations the true residual F − Ku is recomputed and the cancel flag is checked

Fallback no device, not enough memory or no convergence → u is not trusted and the CPU solver takes over

Why PCG a direct GPU factorisation needs 5–20× the matrix's memory; CG needs only the matrix
