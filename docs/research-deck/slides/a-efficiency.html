Appendix 4 · Compute efficiency

GPU path · before May

Why solves were slow · 29 Jul

GPU study · 4–6 Oct

Problem

CPU solves too slow on big meshes

a 50-layer box used all the memory and the GPU solver did not converge

does it all hold in an optimised build, and what does the GPU really gain?

Thinking

a direct GPU factorisation needs 5–20× the matrix's memory and would not fit in 4 GB; CG needs only the matrix

measure where the unknowns go first: 147,084 unknowns, 49.6 % duplicated nodes; 27 % of entries were ties; ties 235× stiffer than nearby elements, so the diagonal spread about 10¹⁰; Jacobi PCG ran 33,400 iterations without converging

solve the same printed part at five mesh sizes, GPU on and off

Solution

CUDA PCG that stays in GPU memory

3 × 3 block Jacobi shared by CPU and GPU; warm starts for fracture steps; a cost model that factorises directly when cheap. Grouping more layers per slab was rejected: it “damages this project's core physics”

release build checked against the full regression

Result

a GPU path from the first commit

printed parts still need many iterations; a layer-aware preconditioner stays open

30 / 30 pass; GPU wins above ~200,000 elements, 2.9× at 367,000; below 60,000 the cost model goes direct

Stages 0 (step 8), 10 and 17 of the iteration history. Ranked remedies in the stage-10 study: share nodes between slabs (−49 % unknowns), conditioning fixes, Tet10 on a coarser mesh, blending the infill into a material. A solid box converges in about 1,350 iterations, a printed part in 64,000–70,000, because thin slabs and ties make the matrix ill-conditioned; the showcase parts (8,000–170,000 elements) therefore ran on the CPU.
